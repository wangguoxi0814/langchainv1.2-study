1. **RAG Rerank 的作用是什么？为什么重排后数据条数不变，噪音还能减少？**

   > 原问题：对RAG Rerank有什么用？ReRank后不还是那么几条数据吗？如果有不想关数据，噪音不还是没有减少吗？

   关键点：
   - Rerank 不减少数量，而是让最相关的排在前面，配合截断和阈值过滤减少噪音
   - 向量相似度是"粗排"，Cross-Encoder 做"精排"，排序更准确
   - 真正减少噪音是组合策略：Rerank 后截断 + 阈值过滤 + 提升信噪比

5. **LangGraph Checkpointer 的保存时机和持久化模式**

   > 原问题：LangGraph的Checkpointer是会在每个节点执行完毕后就保存吗？
   > 原问题：不是有exit\async\sync三种模式吗？默认是哪种模式
   > 原问题：durability不是默认为None吗？

   关键点：
   - 一个超步对应一个 checkpoint，超步内所有节点执行完才保存
   - `durability` 参数签名默认 `None`，但内部逻辑兜底为 `"async"`
   - 源码（main.py:2602-2603）：`if durability is None: durability = config.get(CONF, {}).get(CONFIG_KEY_DURABILITY, "async")`
   - sync：同步写入，容灾最强，延迟最高；async：异步写入，性能更好；exit：仅退出时保存，性能最好
   - `durability` 在 `invoke()` 中指定，不在 checkpointer 构造函数中

7. **PregelTask 的 result 为什么不为空？step 编号和 next 字段的含义**

   > 原问题：`langgraph/src/10_记忆检查点用途.ipynb` 为什么这个PregelTask里，在metadata['step']为0的tasks里面，记录的下游节点的PregelTask的result不为空，这个时候不应该下游节点还没有执行吗？
   > 原问题：不是step=2才是node_output吗？
   > 原问题：step1的next不是指下一个吗？可step=1的next指向的是node_output

   关键点：
   - `result` 来自 `pending_writes`，是"这一步实际执行的结果"，不是"将要执行的结果"
   - `next` 不是"下一步执行谁"，而是"从这个 checkpoint 恢复时，本步骤要执行的节点"
   - 执行顺序：step=-1(__start__) → step=0(node_poem+node_joke) → step=1(node_output) → step=2(END)
   - 源码 `tasks_w_writes()` 中：`task_result if has_writes else None`，有 pending_writes 就有 result
   - 图执行完毕后查看历史，所有 step 的 tasks 都已完成，result 自然不为空
   - 中断场景下，未执行的 task 的 result 为 None

9. **PostgreSQL JSONB 操作符和函数**

   > 原问题：metadata->>'step' 这是什么意思
   > 原问题：按路径取什么意思，metadata#>>'{a,b}' 是取metadata字段的a下面的b吗
   > 原问题：jsonb_array_length(next)和SELECT MAX(metadata->>'step')::text 什么意思
   > 原问题：jsonb是什么意思，这里的jsonb_array_length是操作next这个字段吗？

   关键点：
   - JSONB 是 PostgreSQL 的二进制 JSON 数据类型，支持索引，查询更快
   - `->` 按 key 取值返回 jsonb，`->>` 按 key 取值返回 text
   - `#>>` 按嵌套路径取值，`{a,b}` = `a.b`（如 `metadata#>>'{parents,ns}'` = `metadata.parents.ns`）
   - `jsonb_array_length(next)` 求数组长度，长度为 0 表示图已完成
   - `MAX(metadata->>'step')::text` 取 step 最大值，找执行到了哪一步
   - `::text` 和 `::int` 是 PostgreSQL 类型转换语法
