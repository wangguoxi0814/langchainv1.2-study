## 问题列表

1. **Per-invocation 与 Per-thread 模式下子图检查点可见性差异**

   > 原问题：`24_子图持久化策略.ipynb` "为什么当子图的持久化策略为per_invocation时这里的检查点列表能够看到 messages... 而如果是per_thread,整个检查点状态都是一个[]"

   关键点：
   - `checkpointer=None`（Per-invocation）：继承父图的 checkpointer，子图检查点存在父图的存储中，从父图可查到
   - `checkpointer=True`（Per-thread）：启用独立持久化，子图检查点存在子图自己的存储中，与父图分离
   - `Checkpointer` 类型定义：`None | bool | BaseCheckpointSaver`，`None` 表示继承，`True` 表示独立启用
   - `_defaults()` 解析顺序：先检查 `config` 中是否有父图传递的 `CONFIG_KEY_CHECKPOINTER`，再检查 `self.checkpointer`

2. **Replay 是否追加检查点快照**

   > 原问题：replay是会追加检查点快照是吗

   关键点：
   - Replay 会创建新的检查点快照，原始检查点保留不变
   - 新检查点的 `checkpoint_id` 与原始不同
   - `get_state_history()` 返回所有检查点（包括原始和 Replay 的）
   - Replay 本质上是从指定检查点"分叉"出一条新路径

3. **Stream 中获取父图任务 ID**

   > 原问题：`25_子图流失运行.ipynb` "怎么获取父图的任务ID"
   > 原问题：一个父图每一次invoke都只会有一个taskid,还是invoke时，每个节点都是作为一个任务，因此会有多个taskid

   关键点：
   - Stream 返回的 chunk 是 `(ns, mode, data)` 三元组
   - `ns` 是命名空间元组，格式为 `('节点名:任务ID',)` 或 `('父节点:ID', '子节点:ID')`
   - 每个节点执行都是独立的任务，各自有唯一的 task ID
   - 一次 `invoke()` 会产生多个 task ID（图中有几个节点就几个）
   - 提取方式：`ns[-1].split(':')[-1]`

4. **爷图-父图-子图层级的 Command 指定与节点名冲突**

   > 原问题：`26_子图动态路由.ipynb` "这里如果是爷图-父图-子图层级，graph应该怎么指定，还有这里如果子图和父图有相同的节点名，是不是就是通过graph区分，从而避免冲突的"

   关键点：
   - `Command.PARENT` 是相对的，始终指向上一级，没有 `Command.GRANDPARENT`
   - 多级跳转需要逐级中转：子图 → 父图中转节点 → 爷图
   - 每个图有独立的命名空间，节点名天然不会冲突
   - `graph` 参数用于指定路由目标在哪个层级，不是用来解决命名冲突的

5. **父图能否跳转到子图内部节点**

   > 原问题：父图的节点可以调到子图节点吗？

   关键点：
   - 不支持。`Command` 的 `goto` 只能向上跳转到父图，不能从父图向下跳到子图内部
   - 子图对外是封装的黑盒，父图只看到子图作为一个整体节点
   - 如需控制子图内部路由，可通过输入状态传递标志位、`interrupt` 人工干预、或重新编排子图
